# D-012 — missing picture ⇒ `image-error`, not a silent HOLD

## The workflow that forces this

The receive stage (partner's build) **validates media at intake**: if an incoming email has no usable
article, image or logo, it replies to the sender saying what is missing and the email **fails at
receive**. So by the time a release folder reaches the engine, a usable picture is supposed to exist.

Therefore a picture the image skill cannot find is not an editorial judgement — it is **evidence that the
receive stage let a defect through**, and it must surface as an **Error**, not as a HOLD an editor has to
re-diagnose.

## The rule

1. `pipeline\imgselect.py` returns a **declared asset** (`kind` + `subject`, and a `crop_candidate` when
   the only thing available is a rendered PDF letterhead) when it finds nothing publishable.
2. `pipeline\llm_step.py` then writes `status: "image-error"`, `error_stage: "image"` and
   `error_detail: "no usable picture in the folder — declared <kind> '<subject>'"` into `run.json`.
3. The dashboard shows that release in the error state with the declared subject, so the operator can
   see *what* is missing and *who* to ask — never a bare red row.
4. Validation still fails the article (`FEATURED_DECLARED_ASSET` passes only when a named asset is
   declared; `FEATURED_EXISTS` still fails because there is no file). **Nothing is published.**

## Consequences

- HOLD remains for *editorial* exhaustion (retries used up on a content rule). `image-error` is for a
  **media** gap, and the fix is a message to the sender via the receive stage — not another model run.
- Every `image-error` is a **receive-stage bug report** with a named subject attached, which is what
  makes the 20-article re-test (T-020) useful rather than anecdotal.
- **Tentative.** There is already discussion about merging image selection into the receive skill. If
  that happens, this rule collapses into the intake check — the intake stage would refuse the release
  before the engine ever sees it. Re-open then.
