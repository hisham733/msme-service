# D40 — One repo, one process, one DB for repurpose

## Rule

1. **One repo.** The repurpose engine is vendored under `msme/repurpose/engine/`; the needed set
   is recorded in `docs/repurpose/UPSTREAM.md`. `MSME_AI_News` is the upstream record only and
   is deleted locally after the cut-the-cord test passes.
2. **One process.** The engine runs in a daemon thread inside the FastAPI app on :8899. No
   subprocess, no separate engine dashboard on :8765; the UI is `/repurpose.html` +
   `/api/repurpose/status`.
3. **One DB.** `data/msme.sqlite3` holds receive, filter, auth and repurpose state. The engine
   still writes `run.json` per folder (the folder contract) and the runner mirrors it into
   `repurpose_runs`; `repurpose_exports` replaces `data/repurpose_export.json`.
4. **Needed set only.** Client material, imageeval evidence, corpus, Jev, tools and MG's
   registers are not merged; the referenced decisions and `AGENDA.md` are copied for rationale.
5. **Deps.** `Pillow` and `PyMuPDF` are added to `requirements.txt`.
6. **Cut-over gate.** `MSME_AI_News` is not deleted until the cut-the-cord test passes: the
   synthetic flow runs with the upstream folder absent and reads nothing outside `msme-service`.

## Why

Two repos and two processes made the handover heavy: the partner had to clone both, set
`REPURPOSE_ENGINE_ROOT`, keep two `.env` files and two dashboards, and the state was split between
`run.json`, `data/repurpose_export.json` and the app DB. The seam is small enough to vendor: the
engine is stdlib + Pillow/PyMuPDF, and the app already owns the export and the checklist.
`T-050` records the copy list, phases and proof.

## Supersedes

`D35` (repurpose runs on the external `MSME_AI_News` engine). `D38` still holds for the package
layout; the engine becomes another package under `msme/repurpose/`.
