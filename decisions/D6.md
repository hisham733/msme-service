# D6 — A refused Drive file is needs_human, not success

## Rule

1. The receive accepts a **single Drive file link** (`/file/d/<id>/view`, `?id=<id>`), not only a
   `/folders/` media-kit link. `drive_fetch.fetch_file()` downloads and extracts it when the account may
   download, and returns a typed refusal otherwise.
2. A refusal (`cannotDownloadFile`, `file_too_large`, `unsupported_google_file`, `trashed`,
   `download_failed`) or a download with no extractable text is **`needs_human`**: the run is not
   `success`, the cover note is **not archived** as an article, and the checklist row keeps
   `hasArticle=false`.
3. The reason (including the owner's email when known) goes into the run error, the Flow stage and the
   rejection reply, so the sender is told exactly what to change.

## Why — measured

Email `1a1096dc8c3e8df1` (MSIA Budget 2027) linked a 36,896,175-byte Drive PDF. The pipeline only matched
`/folders/`, so the link was ignored; the run reported `success` and archived a 4.5 KB cover note. The
Drive API then confirmed the file is `canDownload: false` (owner `dayana.arif@msia.org.my`) and a media
request returns `403 cannotDownloadFile` — so no code could have fetched it. Support is still needed for
the next file link that *is* downloadable.

**Rollback.** Revert the `drive_file_fetch` branch and end every run as `success` again; the register
items D6/T-010 record the old behaviour.
